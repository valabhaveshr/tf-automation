# Running & testing tf-automation locally

Everything in `backend/` and `frontend/` was written by agents without a Go or Node
toolchain available — none of it has been compiled, let alone run. Treat step 1 as a real
unknown, not a formality: there will likely be compile errors to fix before anything else
here matters. This doc is the ordered path from "freshly cloned" to "clicked through a
real record creation in the browser."

## 0. Prerequisites

Install on your machine:
- **Go 1.22+** — https://go.dev/dl/
- **Node 20+** — https://nodejs.org/ (or via `nvm`)
- **PostgreSQL 14+** — locally installed, or run via Docker: `docker run --name tf-automation-pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 -d postgres:16`
- **golang-migrate CLI** — https://github.com/golang-migrate/migrate/tree/master/cmd/migrate#installation (or `go install -tags 'postgres' github.com/golang-migrate/migrate/v4/cmd/migrate@latest`)
- A **GitHub account** with permission to create two repos (a test "modules" repo and a test "output" repo) and register a GitHub App — or a personal access token, for a faster first pass (see § 3).

## 1. Make the backend compile

This is the step most likely to surface real bugs — nine parallel agents wrote this
against each other's *reported* signatures, spot-checked but never compiled.

```bash
cd backend
go mod tidy          # generates go.sum, resolves transitive deps — needs network access
go build ./...        # THE real first checkpoint
go vet ./...
```

Fix whatever `go build`/`go vet` surface. Likely trouble spots, in rough order of
suspicion (per the agents' own "double-check" notes):
- `backend/internal/codegen` — the golden-file tests' expected output bytes were
  hand-derived, not generated by `hclwrite` itself. Run `go test ./internal/codegen/... -run TestGolden -update` to regenerate them from the real library output, then `git diff` to sanity-check nothing unexpected changed, before trusting that package.
- `backend/internal/output` and `backend/internal/catalog` — go-github v63 API surface (struct/method names) was written from memory, not confirmed against the vendored source.
- `backend/internal/auth/oidc.go` — go-oidc/v3 API surface, same caveat.
- Anywhere `data.Store`'s pgx v5 scanning meets `uuid.UUID`/`jsonb` columns.

Once it builds:
```bash
go test ./... -short   # unit tests that don't need Postgres
```
Tests in `internal/data` (`roles_test.go`, `audit_log_test.go`) are gated on
`TEST_DATABASE_URL` and will skip without it — see § 2 for setting that up.

## 2. Postgres + migrations

```bash
createdb tf_automation   # or: docker exec -it tf-automation-pg createdb -U postgres tf_automation

export DATABASE_URL="postgres://postgres:postgres@localhost:5432/tf_automation?sslmode=disable"
migrate -database "$DATABASE_URL" -path backend/db/migrations up
```

This applies both `000001_init` (Phase 1 schema) and `000002_roles_and_audit_log`
(Phase 3 schema — roles, user_roles, audit_log, and the users table's new columns).
`000002`'s backfill only touches rows that exist *at migration time*, so run it before
seeding your first user (§ 4), not after.

To run the data-layer tests against this database:
```bash
export TEST_DATABASE_URL="$DATABASE_URL"
cd backend && go test ./internal/data/...
```

## 3. A test modules repo and output repo on GitHub

Create two **new, empty** repos (they don't need to be public):
- `<your-account>/tf-automation-modules` — the catalog source
- `<your-account>/tf-automation-output` — where generated code lands

In the modules repo, add at least one module following the convention (see
`contracts/var-schema.example.json` for the shape this exercises). Modules can sit
directly under `modules/` or be nested in subfolders to any depth — the module's name
is its folder path under `modules/` (`vm-instance`, or `compute/instance` for
`modules/compute/instance/`), and that full path is what goes in the tag:

```
modules/
  vm-instance/
    variables.tf
    metadata.yaml
  compute/
    instance/          # nested: module name "compute/instance", tag compute/instance/v1.0.0
      variables.tf
      metadata.yaml    # name: instance   (or name: compute/instance)
```

`variables.tf`:
```hcl
variable "size" {
  type    = string
  default = "Standard_B2s"
}
variable "image" {
  type = string
}
variable "admin_password" {
  type      = string
  sensitive = true
}
variable "name" {
  type = string
}
```

`metadata.yaml`:
```yaml
name: vm-instance
display_name: "Virtual Machine Instance"
category: "Compute"
cloud: "azure"
description: "Provisions a single VM."
instance_label_field: "name"
```

Commit both files to `main`, then **tag the commit** — module versioning is entirely
tag-driven, an untagged module never appears in the catalog. The tag prefix is the
module's path, either relative to `modules/` or including it — both forms name the same
module, and the highest version across them wins:
```bash
git tag vm-instance/v1.0.0
git tag compute/instance/v1.0.0             # for modules/compute/instance
git tag modules/compute/instance/v1.1.0     # same module, prefixed form
git push origin main --tags
```
If your modules folder isn't called `modules`, set `MODULES_PATH` for the backend (§ 4).

**Credentials** — for a fast first pass, use a PAT instead of registering a GitHub App:
create a classic PAT with `repo` scope on your account, covering both repos.
(A real GitHub App, per the locked decision, is still the right choice before this goes
near production — see `plan/ARCHITECTURE.md`'s Phase 0 section for what permissions it
needs. Swapping the PAT for App credentials later is just an env var change.)

## 4. Backend: configure, seed a user, run

```bash
cd backend
export HTTP_ADDR=":8080"
export DATABASE_URL="postgres://postgres:postgres@localhost:5432/tf_automation?sslmode=disable"
export JWT_SIGNING_SECRET="dev-secret-change-me"
export GITHUB_TOKEN="ghp_..."                    # the PAT from § 3
export MODULES_REPO_OWNER="<your-account>"
export MODULES_REPO_NAME="tf-automation-modules"
export OUTPUT_REPO_OWNER="<your-account>"
export OUTPUT_REPO_NAME="tf-automation-output"
export GITHUB_WEBHOOK_SECRET="dev-webhook-secret" # required even if you skip real webhooks (§ 6)
export STATE_BACKEND="gcs"
export STATE_BACKEND_BUCKET="dev-tfstate-bucket"  # doesn't need to actually exist for Phase 1 — no apply happens
# OIDC_* left unset = SSO disabled, password-only login (fine for local testing)
```

Seed a login (Phase 1 has no signup endpoint by design — see `internal/config/config.go`'s
bottom comment — so `backend/cmd/seed-admin` exists specifically to make local testing
possible):
```bash
go run ./cmd/seed-admin -username admin -password "a-real-password"
```

Run the server:
```bash
go run ./cmd/server
```

## 5. Frontend

```bash
cd frontend
npm install
npm run build   # tsc --noEmit first — the other real "does this compile" checkpoint
npm run dev
```
The dev server proxies `/api` to `http://localhost:8080` by default (see
`vite.config.ts`'s `TF_AUTOMATION_API_PROXY`, per WS-H's report — override it if your
backend is elsewhere). Open the printed local URL.

## 6. Manual smoke test (mirrors Phase 1's Exit Criteria)

1. Log in as `admin` / the password you seeded.
2. You should see an admin-only **"Refresh catalog"** control. Click it — this calls
   `POST /api/catalog/refresh`, which scans your modules repo's tags and should pick up
   `vm-instance` at `v1.0.0`. (There's no webhook listener reachable from GitHub on
   `localhost` without a tunnel, so manual refresh is the practical path for local
   testing — real push/tag webhooks need a public URL, e.g. via `ngrok`, pointed at
   `POST /api/webhooks/github/modules` with `GITHUB_WEBHOOK_SECRET` matching what you
   configure on the GitHub repo's webhook settings.)
3. `vm-instance` should now appear in the catalog browser. Select it, add an instance
   (fill `size`/`image`/`admin_password`; note `admin_password` is `sensitive` — the UI
   should show a warning that it's still included in the generated tfvars, per the locked
   Phase 1 decision), fill customer/project/env, and preview.
4. Confirm the preview shows `main.tf`, `variables.tf`, and `vm-instance.auto.tfvars`
   (not a combined `terraform.tfvars` — per-service tfvars is the locked decision).
5. Save. Check your output repo on GitHub — a new commit should have landed at
   `<customer>/<project>/<env>/`, including a one-time `backend.tf`.
6. Reopen and edit the record; confirm the form repopulates and the diff view shows only
   your actual change.
7. Optional but worth doing given nothing here has run before: clone the output repo
   locally and run `terraform init -backend=false && terraform validate` against the
   generated directory — this is the strongest signal the generated HCL is actually
   correct, not just well-formed.
8. Log out, log back in as a non-admin user (seed one without the admin grant by using a
   fresh username with `seed-admin` and then manually revoking admin, or just create a
   second user directly via SQL) and confirm the "Refresh catalog" control and the
   `/admin/audit-log` page are both absent.
9. As the admin user, visit the audit log page and confirm your record create/update and
   the catalog refresh all show up with your username as actor.

## 7. Testing SSO (Phase 3, optional)

Needs a real OIDC provider (Azure AD/Entra, Okta, Google Workspace, Auth0, Keycloak — any
standards-compliant one). Register an app/client there with redirect URI
`http://localhost:8080/api/auth/sso/callback`, then set:
```bash
export OIDC_ISSUER_URL="https://your-idp/..."
export OIDC_CLIENT_ID="..."
export OIDC_CLIENT_SECRET="..."
export OIDC_REDIRECT_URL="http://localhost:8080/api/auth/sso/callback"
```
Restart the server. The frontend login page should now show an SSO button in addition to
the password form. First login via SSO creates a new local user with the `requester`
role; if a local-login user already exists with the same username, it gets linked to the
SSO identity instead (see `backend/internal/api/oidc_adapter.go`'s doc comment for the
exact linking/collision rules).

## 8. What "done" looks like vs. what's still unverified

Getting through § 1–6 without giving up is itself the main open question right now.
Once it works, the things still worth deliberately testing (not yet exercised by anyone,
human or agent):
- Concurrent saves to the same `(business_short_code, env, resource_type)` naming
  counter actually never collide under real Postgres (only tested against an in-memory
  fake so far).
- A deliberately stale edit (open a record in two tabs, save from both) actually returns
  409, not a silent overwrite.
- Killing the server mid-save (between the DB commit and the GitHub commit) leaves
  `sync_status=failed` or `pending`, and retry-sync actually recovers it.
